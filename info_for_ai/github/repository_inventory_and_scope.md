# Repository inventory and bulk scope

## Activation

Load this module only for work concerning the user's own GitHub repositories when either the exact repository has not been supplied and one must be located or selected, the task spans multiple or all repositories, or the selected workflow performs repository-maintenance operations whose scope depends on archival or development status.

## Inventory and scope contract

**Invariant:** `../info_user/repositorios_github.csv` is the canonical repository inventory and `../info_user/repositorios_github_lookup.csv` is only a physical locator from repository name to CSV line. When an exact repository name is supplied, match it case-insensitively in the lookup and read only the exact canonical inventory row named there before broader repository discovery or mutation. If the lookup is missing, stale, inconsistent, or does not contain the supplied name, fallback only to a bounded scan of the canonical inventory sufficient to resolve that name; report a lookup inconsistency when one is demonstrated rather than replacing the inventory with an unscoped GitHub-wide search.

**Invariant:** Open the canonical inventory before repository discovery or mutation when either the exact repository has not been supplied and one must be located or selected, the task spans multiple or all repositories, or the selected workflow requires recorded `estado_desarrollo` or `archivado`. For an exact repository resolved through the lookup, the exact canonical row satisfies this requirement. Use the CSV as the candidate inventory and as the recorded source for `estado_desarrollo` and `archivado`.

**Default:** After applying the command- or module-specific inventory filters, do not enumerate all accessible repositories merely to refresh metadata. Treat the maintained inventory as the scope authority and refresh current GitHub repository metadata lazily, only for repositories whose live state is needed to interpret an actionable result, perform a mutation, resolve a material discrepancy, or satisfy an explicit requirement of the selected workflow. Prefer a targeted repository lookup over a full repository enumeration. Use a complete live repository inventory only when the task itself requires one or when the maintenance procedure is synchronizing `repositorios_github.csv`. Before any mutation, perform the live verification required by `00_core.md`.

**Invariant:** The maintained CSV is ordered in contiguous active-or-operational, frozen, and archived blocks. For operational workflows that exclude frozen and archived repositories, when the reader supports bounded sequential reads, consume the CSV from the beginning in bounded chunks and stop as soon as the first frozen or archived entry begins the excluded tail. Start with bounded reads rather than requesting the complete CSV and relying on truncation. Do not request or parse the complete CSV when bounded reads can establish the required scope. Parse the complete CSV only when bounded reads are unavailable, the ordering invariant cannot be trusted or validated, or the task itself genuinely requires records beyond the bounded operational scope.

**Invariant:** For Dependabot, repository-security automation, GitHub Actions, workflows, checks, runs, branch or worktree maintenance, or analogous bulk operational maintenance over the user's repositories, exclude entries with `archivado=si` or `estado_desarrollo=congelado`. When one repository is explicitly supplied for one of these maintenance tasks, still check its inventory status before acting. Do not inspect or mutate an excluded repository unless the user explicitly asks to include that repository despite its archived or frozen status.

If a repository required by the task is absent from the inventory, use a targeted remote lookup for that repository and report the discrepancy instead of silently broadening the search. If a downstream discovery operation cannot establish trustworthy coverage for a repository because of permissions, tool limitations, truncation, or ambiguous access, keep that repository in the coverage record as unverified and do not convert an empty or skipped result into evidence that it has no relevant work. A separate repository-metadata sweep is not required for a verified zero-result claim when the downstream discovery itself trustworthily covers the exact inventory-selected repository set and the conclusion does not depend on unverified live metadata. When live metadata is fetched and reports the repository as archived or disabled, or materially conflicts with the recorded identity or archival state, use the more restrictive state for the current operation, report the discrepancy, and do not mutate the repository unless the user's explicit scope permits it. If the inventory cannot be read, do not start a multi-repository operation that depends on it.

**Invariant:** For generic search capabilities that accept several repositories at once but do not explicitly guarantee complete set semantics, do not treat one large multi-repository empty result as proof that every repository in scope is empty. Prefer bounded sequential batches, normally about 5-8 repositories, and preserve a coverage record for the resolved repository set. If a batch result is ambiguous because of an error, truncation, unsupported filtering, or observed inconsistency, subdivide only that batch until coverage is established or a concrete limitation is reached. Do not fan out to one request per repository unless subdivision or repository-specific confirmation is actually needed. This safeguard does not require redundant batching when using an official organization-level or equivalent bulk endpoint whose contract explicitly provides the requested inventory across the full scope.
